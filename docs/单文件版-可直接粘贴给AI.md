# meeting-minutes · 会议纪要技能（单文件合订版）

> 用法：**整份复制，粘贴进 AI 对话**，然后说"按这个技能把下面的录音/文字整理成会议纪要"。
> 脚本部分（转写 / 质检）需要另存成 `.py` 文件才能跑，纯文字流程不受影响。

# 第一部分 · 主流程

# 会议纪要工作流（meeting-minutes）

## 用途

把一场会议的原始材料（录音 / 转写稿 / 文字记录）变成**可以直接发出去**的会议纪要，外加一份可汇报的 PPT。贯穿全流程的核心约束：

> 所有"共识""方案""行动项"必须能在原话里找到依据，找不到就写"待确认"。

相比"让模型直接写一篇纪要"，本技能强制多做三件事：

1. **骨架先行** —— 按会议类型套固定章节模板，不让模型自由发挥结构。
2. **要点先行、原文即弃** —— 先按议题切段提炼结构化要点，提炼完清掉原文，最后全局去重出稿。
3. **证据 + 质检兜底** —— 每条关键结论挂原文出处；出稿后跑自动质检，**质检只管查，不管补**。

## 何时使用

- 用户上传会议录音（.mp3/.wav/.m4a/.amr/.mp4）或已有转写稿
- 用户粘贴会议文字记录，要求"整理成纪要"
- 用户要求"把这次会议做成汇报 PPT""出一版会议纪要"
- 用户要求"把会议里的待办 / 决策 / 需求 / 未解决问题拎出来"

## 不可违反的铁律

| # | 铁律 | 违反后果 |
|---|------|---------|
| R1 | 所有"共识 / 方案 / 决策 / 行动项 / 技术要点"必须携带原文出处（文件+行号，或 时间戳+发言人）。找不到出处 → 内容写"待确认"。 | 质检 Q1 失败，不可交付 |
| R2 | 模板选定的章节标题不得删除；本次不涉及 → 正文写"本次不适用"。 | 质检 Q2 失败 |
| R3 | 行动项必须有责任人 + 交付物 + 截止日；缺失字段写"待确认"，不得留空、不得编造。 | 质检 Q3 失败 |
| R4 | 不得出现原文中不存在的数字、日期、人名、承诺。听不清的人名/数字/日期一律标 `[?]`，**不猜**。 | 质检 Q4 失败 |
| R5 | 同一件事只在"意见总结"章节说一次，不拆到多章重复讲。 | 质检 Q5 失败 |
| R6 | 每个阶段结束必须追加一条节点记录（checkpoint），只追加、不涂改。 | 过程不可追溯 |
| R7 | 会议背景压到 3 句话以内，直奔主题。 | 头重脚轻，读者抓不到重点 |
| R8 | 修复质检失败项时只允许两个动作：**标注"待确认"** 或 **删除**。禁止为了让质检通过而补写原文没有的内容。 | 纪要说谎 |

## 工作流

六个阶段，每阶段结束写一条 checkpoint。阶段不可跳过、不可合并。

### Phase 0 · 建档与确认（CP0）

1. 确认输入材料可读取，并**判出档位**（甲=有文字稿 / 乙=录音待转写）—— 判定规则见 Phase 1 第 0 步。**甲档不要碰转写，直接进 Phase 2。**
2. **一次性**问清 4 件事，不要反复打断用户：
   - 会议类型：跨部门对接会 / 内部工作会 / 决策评审会 / 外部沟通会
   - 输出形态：Word 纪要 / PPT 汇报 / 两者都要
   - 参会人与角色、会议时间、地点、主持人
   - 输出语言

   **同时主动告知两件事**（不告知等于埋雷）：
   - **转写默认没有说话人分离** —— 所有行动项的"责任人"只能写"待确认"。若用户要真实责任人，需在 Phase 5 拿人名表回填。
   - **录音质量决定纪要上限** —— 手机远距离录制、多人抢话的音频，转写准确率会显著下降，专有名词大概率错。
3. 建工作目录与 meta.md：
   ```bash
   python scripts/init_meeting_workspace.py "结算流程改版评审会" \
       --dir "<输出根目录>" --type 决策评审 --date 2026-09-18 \
       --location "3F 会议室A" --attendees "张三(主持),李四,王五" --output both
   ```
4. 写节点记录：
   ```bash
   python scripts/append_checkpoint.py "<工作目录>" --id CP0 \
       --phase "Phase 0 建档与确认" --output "meta.md" \
       --basis "用户口述的会议元信息" --status 完成 \
       --pending "待补：参会人王五的角色" --next "CP1 转写"
   ```
5. **自己手上记一份事实清单**（参会人、地点、会议背景、议题范围）——Phase 5 复核用。

### Phase 1 · 取得文字稿（CP1）—— 三条路，只走一条

**转写不是必经步骤，只是三种拿稿方式之一。** 这一步最容易把整个流程卡死，所以必须先判档、再动手。

#### 第 0 步：判定输入档位

| 档位 | 用户的输入 | 走哪条路 |
|---|------|------|
| **甲** | 已有文字稿：转写稿 / 会议速记 / 聊天记录 / 字幕文件 | **路 1** —— 永远不要碰转写脚本 |
| **乙** | 只有录音，且 doctor 判定可转写 | **路 2** —— 本地离线转写 |
| **丙** | 只有录音，doctor 判定不可用，或转写下载失败 | **路 3** —— 转人工供稿 |

#### 路 1 · 直接用现成文字稿（甲档）

把用户给的文字整理成 `01-转写稿.md`，统一成逐行格式（便于后续质检回溯）：

```
1. [00:00:12] 张三：……
2. [00:00:35] 李四：……
```

- 原稿没有时间戳 → 用序号行号代替（`[L12]`），出处照样可回溯。
- 原稿没有发言人 → 写「发言人未分离」，责任人一律"待确认"。
- **不要因为"没有录音就没走转写"而心虚**，这条路产出的纪要质量通常最高。

#### 路 2 · 本地离线转写（乙档）

**先跑体检，不要上来就下载**（体检 10 秒，盲试一轮 10 分钟起）：

```bash
python scripts/doctor.py --size medium --json "<工作目录>/doctor.json"
```

脚本会给出明确结论：路径 A（立即可跑）/ B（需下载 N MiB）/ C（本机不可用）。
**拿到 C 立刻转路 3，不要自己想办法。**

判定 A/B 后：

```bash
# 1) 先试跑前 60 秒确认音质（约 1-2 分钟）
python scripts/transcribe.py "<音频路径>" --out "<工作目录>/01-转写稿.md" --limit 60

# 2) 可用则跑全量（medium 模型约 1.9 倍实时：18 分钟音频 ≈ 10 分钟）
python scripts/transcribe.py "<音频路径>" --out "<工作目录>/01-转写稿.md"
```

脚本自动装依赖（腾讯云源）、自动下载模型（hf-mirror 断点续传）、自动归一化音量、分块转写并落进度文件（中断加 `--resume` 续跑）。

- 听不懂的人名、数字、日期、决定 → 标 `[?]`，**不猜**。
- **转写缺口必须单列**：存在整段无法还原的时间区间时，在 `02-要点.md` 末尾单列「转写覆盖缺口」表，标注起止时间与原因，该区间内容**不进纪要正文**，一律进待确认清单。

> **两个已实测的转写坑**
> - **不要给 initial_prompt 写任何句子**。提示词里的词组（哪怕是"参会者在讨论工作方案"这种中性描述）会被模型当成台词吐出，形成几十次重复的幻觉段。脚本默认不传 initial_prompt。
> - **远场/手机远距离录音必须用 medium 及以上**。small 在这种音质下产出的文本基本不可读；实测 medium 约 1.9 倍实时，可接受。

#### 路 3 · 转人工供稿（丙档）

**判定不可用后，立即停止一切转写尝试**，把下面三条通道交给用户，然后等他给稿子：

1. **会议平台自带纪要** —— 腾讯会议 / 飞书妙记 / 钉钉闪记 都自带「转写 + 自动纪要」，导出文字稿即可，准确率高于本地离线转写。**最省事**。
2. **手机录音机自带转写** —— iPhone 备忘录录音、小米/华为/OPPO 录音机多有「转文字」，导出后直接用。
3. **剪映 / 讯飞听见 / 网易见外** —— 导入音频导出字幕或文稿，多数有免费额度。

用户实在拿不到稿子时，生成一份人工补录模板让他边听边填：

```bash
python scripts/make_manual_template.py "<音频路径>" --out "<工作目录>/01-转写稿.md"
```

拿到稿子后按**路 1** 继续，从 Phase 2 开始，转写这步整个跳过。

#### 三条死规矩（违反必翻车）

| # | 规矩 | 为什么 |
|---|---|---|
| T1 | **转写最多试一次**：一次 doctor + 一次下载。失败立刻转路 3。 | 换着花样重试（换源、换模型、换引擎）每次都是十分钟级消耗，用户等到崩溃，成功率还极低 |
| T2 | **禁止用浏览器自动化去蹭在线转写网站**。 | 这类站点要登录/验证码/付费，自动化成功率接近于零，却能耗掉十几轮对话 |
| T3 | **不许对用户说"我再试试别的办法"**。 | 说了就是没有决策。要么给出上一步的明确结论，要么转路 3 把通道交给用户 |

#### 收尾（三条路共用）

写 checkpoint CP1，记录：稿子来源（路 1/2/3）、覆盖率、`[?]` 数量、失效区间。
路 3 的 checkpoint 必须写明「本机不具备转写条件，已转人工供稿」。

### Phase 2 · 切段提炼（CP2）—— 最关键的一步

**目标：把长转写稿压成结构化要点，并且提炼完就把原文清出上下文。**

1. **按议题切段**。默认按话题切换切；满足任一条件必须切段：时长 > 30 分钟、转写稿 > 8000 字、出现议题转换词（"下面看第二个议题""这块先告一段落"）。
2. **逐段处理，原文即弃**：每次只把一段原文读进上下文 → 提炼 → 写盘 → 不再回读该段原文。
   **禁止把整篇转写稿一次性读进上下文。**
3. 每段产出固定六栏：
   ```
   ### 段3 · 结算流程改版（00:12:00 - 00:22:30）
   - 议题：……
   - 发言要点：……（后用  出处：L120-L124 · 00:12:30 · 张三）
   - 结论/决定：……
   - 数字与日期：结算周期 14 天（L138）；上线日 2026-10-15（L201）
   - 待确认：[?] 项
   - 未解决问题：……
   ```
4. 全部段落写进 `02-要点.md`。
5. 写 checkpoint CP2，记录段数、要点条数、`[?]` 数量。

> 上下文里始终只保留"结构化要点"。原文留在硬盘的 01 文件里，供 Phase 4 质检回溯。

### Phase 3 · 合并去重与出稿（CP3）

1. **全局去重**：同一事项在多个段落出现 → 合并为一条，出处置处引用。
2. **归集到"意见总结"**：需求、共识、决策、技术要点全部合并进同一章节，一次说完，不拆到多章来回讲。
3. **选模板**：按 meta.md 的会议类型，从 `references/templates.md` 取对应章节骨架。
4. **过滤 + 动态编号**：剔除本次无内容的章节，剩余章节按顺序重新编号；被保留的章节标题一字不改，无内容写"本次不适用"。
5. **挂证据**：每条要点写成"要点 + 证据字段"结构，格式见 `references/evidence-and-qc.md`。质检脚本依赖此格式，**格式不能自创**。
6. 输出 `03-纪要初稿.md`。
7. 写 checkpoint CP3。

### Phase 4 · 质检（CP4）—— 只查不补

1. 跑确定性检查脚本：
   ```bash
   python scripts/qc_check.py "<工作目录>/03-纪要初稿.md" \
       --transcript "<工作目录>/01-转写稿.md" \
       --template 决策评审 \
       --out "<工作目录>/04-质检报告.md"
   ```
2. 脚本覆盖可机器判定的部分：出处缺失、章节缺失、行动项缺字段、数字/日期查无来源、重复条目。
3. 模型再补判脚本覆盖不到的部分：章节顺序是否合理、措辞是否与原文语气一致、有没有"看起来很对但原文没说"的句子。
4. 输出 `04-质检报告.md`：结论 PASS / FAIL + 逐条问题 + 修复动作。
5. FAIL → 回 Phase 3 修复，遵守 R8（只允许标注"待确认"或删除）。
6. 写 checkpoint CP4。

### Phase 5 · 交付（CP5）

1. **事实复核**：拿 Phase 0 记录的事实清单（参会人、地点、背景信息），逐条核对纪要中的事实，结合质检结果删改。
2. 按需生成交付物：
   - Word 纪要 → 路由 `tencent-docx` 技能，按 `references/output-formats.md` 的 Word 版式出 `会议纪要.docx`
   - PPT 汇报 → 路由 `tencent-pptx` 技能，按同文件的 PPT 页序出 `会议汇报.pptx`
   - `待确认清单.md` —— 所有"待确认"条目汇总成表，附建议确认对象
   - `图文摘要.md` —— 要点卡片
3. 写 checkpoint CP5，标注交付物清单与未解决项。
4. 用 present_files 一次性展示交付物。

## 脚本

| 脚本 | 用途 | 何时跑 |
|---|---|---|
| `scripts/init_meeting_workspace.py` | 建工作目录 + meta.md + checkpoints.md 骨架 | Phase 0 |
| `scripts/doctor.py` | **环境体检**，10 秒给出「能不能转写 / 走哪条路」 | Phase 1 第 0 步（有录音时必跑） |
| `scripts/transcribe.py` | 本地离线转写（自动装依赖/下模型/分块续跑） | Phase 1 路 2 |
| `scripts/make_manual_template.py` | 生成人工补录模板（边听边填） | Phase 1 路 3 |
| `scripts/append_checkpoint.py` | 追加一条节点记录（自动取真实时间戳） | 每阶段末 |
| `scripts/qc_check.py` | 确定性质检，产出 04-质检报告.md | Phase 4 |

六个脚本都支持 `--help`。**不要自己拼时间戳**，交给 `append_checkpoint.py`。

`doctor.py` 常用参数：`--size base|small|medium`、`--json <路径>`（结构化结论给 AI 读）、`--skip-network`（离线体检）。
退出码 0 = 可转写（A/B），**3 = 本机不可用，立刻转路 3**。

`transcribe.py` 常用参数：`--model base|small|medium`（默认 medium；下载不动先试 base，仅 138 MiB）、`--limit N`（只转前 N 秒试跑）、`--resume`（续跑）、`--model-dir <目录>`（手动下载后指定）、`--language zh`、`--chunk 120`、`--threads 8`。

## 常见失败模式

- **在转写上反复试错**（换源、换模型、蹭在线网站）→ 每轮十分钟级消耗，用户等到崩溃，成功率极低。先跑 `doctor.py`，拿结论办事；判定不可用立刻转路 3（见 Phase 1 三条死规矩）。
- **有现成文字稿还去跑转写** → 纯浪费。甲档直接走路 1，永远不要碰转写脚本。
- **一口气读完转写稿再写纪要** → 上下文被原文塞满，中段细节丢失。必须分段处理、原文即弃。
- **章节按模型喜好自由发挥** → 每份纪要结构都不一样，无法横向对比。必须先套模板。
- **质检只写在提示里不跑脚本** → 模型对自己写的稿子会自我宽容。脚本产出可读报告，能被人复核。
- **为了让质检通过而补内容** → 宁可留"待确认"。待确认清单本身就是交付价值，不是瑕疵。
- **行动项混在正文段落里** → 质检脚本抓不到，责任人/截止日静默丢失。行动项必须独立成章、独立成条。

# 第二部分 · 章节模板（四套）

# 章节模板（Phase 3 用）

## 一、通用规则（四套模板共用）

1. **标题不删**：模板里出现的章节标题必须原样保留。本次会议不涉及 → 正文写"本次不适用"。
2. **背景压 3 句**：`会议背景` 最多 3 句话，写完直奔议题。
3. **每套不超过 5 章**。要加内容，往这 5 章里加，不新开章。
4. **动态编号**：过滤掉"本次不适用"的章节后，剩余章节按 1、2、3… 重排。
   允许整章删除的**唯二**情况：
   - (a) 该章不在本次会议类型的模板里；
   - (b) 整章无内容且全篇讨论中无任何痕迹（说明确实是空议题）。
   其余一律保留标题 + 写"本次不适用"。
5. **意见总结是唯一收口**：需求、共识、决策、技术要点全部进 `意见总结`，禁止拆到"议题讨论""结论""决定"等多个章节来回讲。
6. **行动项独立成章**，不写在正文段落里，保证能被质检脚本抓到。
7. 每条要点必须挂证据字段，格式见 `references/evidence-and-qc.md`。

## 二、会议类型判定

| 类型 | 判定关键词 | 特征 |
|---|---|---|
| 跨部门对接会 | 对接、协同、配合、双方、接口、流程拉通、上游/下游 | 有多方分工，需要明确交接与责任边界 |
| 内部工作会 | 周会、例会、站会、进展、同步、内部、组内 | 以进度同步和阻塞清理为主 |
| 决策评审会 | 评审、立项、评审会、方案过会、是否通过、拍板 | 有明确评审对象与通过/否决结论 |
| 外部沟通会 | 客户、甲方、乙方、供应商、外部、来访、洽谈 | 有对外承诺，需区分我方/对方行动项 |

判定不出 → **问用户**，不要猜。会议类型决定骨架，猜错等于全篇返工。

## 五、动态编号示例

模板 A 原始 5 章，本次会议不涉及"待确认与风险"（无风险、无待确认项）：


## 六、章节命名硬约束

- 一级章节用 `## 1. 标题`；二级用 `### 1.1 标题`。质检脚本靠这个格式认章节，格式不能改。
- 章节标题内不出现标点以外的修饰（不写"## 1. 会议背景（很重要）"）。

# 第三部分 · 证据字段与质检规范

# 证据卡与质检规范

## 一、证据字段格式（机器可解析，不得自创）

每条要点 = 一个列表项 + 若干缩进字段。缩进用 **2 个空格**，字段名用中文全角冒号。

```markdown
- **决策 D1**：Q3 上线新结算流程，旧流程并行保留 1 个迭代
  - 状态：已决策
  - 责任人：李四
  - 交付物：上线方案 + 回滚预案
  - 截止日：2026-10-15
  - 出处：01-转写稿.md L120-L124 · 00:12:30 · 张三
  - 引用：「结算这块我建议 Q3 上，老流程先别删，留一个迭代兜底」
```

要点行格式：`- **<类型> <ID>**：<一句话结论>`

- **类型**枚举：`需求` `共识` `决策` `技术要点` `行动项` `方案` `风险` `问题` `进展`
- **ID**：类型首字母 + 序号（如 `决策 D1`、`行动项 A3`、`需求 R2`）。同类内连续编号。

## 二、字段清单

| 字段 | 适用类型 | 必填 | 说明 |
|---|---|---|---|
| 状态 | 全部 | 是 | 见下方状态枚举 |
| 责任人 | 行动项、方案 | 是 | 未定写"待确认"，不留空 |
| 交付物 | 行动项 | 是 | 未定写"待确认" |
| 截止日 | 行动项 | 是 | 未定写"待确认"，**不得推测日期** |
| 出处 | 全部（除状态=待确认） | 是 | `文件名 L行号-L行号 · 时间戳 · 发言人` |
| 引用 | 全部（除状态=待确认） | 建议 | 逐字原文，≤50 字，**不得改写、不得拼接** |
| 依据 | 决策 | 是 | 决策所依赖的原话或数据出处 |

## 三、状态枚举

| 状态 | 含义 | 可否缺"出处" |
|---|---|---|
| 已确认 | 会上明确同意，有原话 | 否 |
| 已决策 | 会上拍板定案 | 否 |
| 待确认 | 会上没定 / 听不清 / 找不到依据 | 是（出处写"未找到出处"，并说明原因） |
| 已否决 | 会上明确否定 | 否 |
| 已延期 | 明确推迟到下次 | 否 |

状态只能取这五种。**不要让"待确认"承担"我不确定但我猜是这样"的语义** —— 猜出来的内容一律删除（R8）。

## 四、出处三种形态

| 材料形态 | 出处写法 |
|---|---|
| 转写稿（转写自录音） | `01-转写稿.md L120-L124 · 00:12:30 · 张三` |
| 用户粘贴的文字记录 | `用户提供的文字记录 第3段`（若用户给了行号则写行号） |
| 用户口述补充（会前/会后） | `用户口述 2026-09-18 补充` |

出处必须能被人复核到。写不出来源 = 来源不存在 = 改状态为"待确认"。

## 五、质检五项（Phase 4）

**质检只管查，不管补。** 发现问题只输出问题与修复动作，不代写内容。

| 编号 | 检查项 | 判定方法 | 不通过条件 |
|---|---|---|---|
| Q1 | 可回溯性 | 所有 `共识/方案/决策/行动项/技术要点/需求` 条目是否都有"出处"字段 | 任一条件条目的状态≠待确认 且 出处缺失或为"未找到出处" |
| Q2 | 章节完整性 | 对照 `references/templates.md` 的类型模板，一级章节标题是否全部存在 | 任一模板章节标题缺失 |
| Q3 | 行动项三要素 | 每条"行动项"是否有 责任人 / 交付物 / 截止日 | 任一字段整体缺失（值为"待确认"算通过，但计入待确认清单） |
| Q4 | 无凭空内容 | 抽出纪要正文里的所有日期、金额、百分比、数量，回原文比对 | 任一数字/日期在原文中查无来源 |
| Q5 | 去重 | 同类条目标题归一化后比对 | 同一事项在两章或多条重复出现 |

补充说明：

- **Q3 与 Q1 的"待确认"是有价值的输出**：它变成 `待确认清单.md`，不是失败。真正的失败是字段缺失（静默丢信息）。
- **Q4 只比对数值型事实**（日期、金额、百分比、数量、人名）。措辞改写不算凭空内容，但结论方向不能反。
- **Q2 豁免**：模板里允许整章删除的两种情形（不在该类型模板内 / 整章确实无内容），需在质检报告中写明删除理由，否则判不通过。
- 脚本覆盖不到的部分由模型补判，至少覆盖这三条：章节顺序是否合理、结论措辞是否与原文语气一致、有无"看起来很对但原文没说"的句子。

## 六、质检报告格式（04-质检报告.md）

```markdown
# 质检报告 · <会议名>

- 检查对象：03-纪要初稿.md
- 对照模板：跨部门对接
- 结论：**FAIL**（4 项通过 / 1 项未通过）
- 生成时间：2026-09-18 14:20

| 检查项 | 结果 | 问题条目 | 修复动作 |
|---|---|---|---|
| Q1 可回溯性 | PASS | — | — |
| Q2 章节完整性 | PASS | — | — |
| Q3 行动项三要素 | FAIL | A2 缺截止日；A5 缺责任人 | 回 Phase 3，字段值写"待确认" |
| Q4 无凭空内容 | PASS | — | — |
| Q5 去重 | PASS | — | — |

## 需人工补判项
- 章节顺序：…
- 措辞与语气：…
- 疑似无依据结论：…

## 修复后复核
（修复完成后重跑 qc_check.py，把新报告覆盖本文件，并追加一条 checkpoint）
```

## 七、修复动作白名单（R8）

质检 FAIL 后允许的动作，**只有这两个**：

1. 把内容或字段标注为"待确认"
2. 删除该条目

禁止：补写原文没有的内容、把数字改成"看起来更合理"的数字、为了让 Q3 通过而编个截止日、为了 Q1 通过而编个行号。
**编造行号是最危险的违规** —— 它会让整份纪要失去可复核性。

## 八、待确认清单格式（交付物）

```markdown
# 待确认清单 · <会议名>

| # | 事项 | 类型 | 缺失/存疑点 | 建议确认对象 | 影响 |
|---|---|---|---|---|---|
| 1 | 新结算流程上线日 | 行动项 A2 | 截止日未定 | 李四 | 影响排期 |
| 2 | 发言人 [张三/张山] | 事实 | 姓名听不清 | 会议主持人 | 影响纪要权威性 |
```

# 第四部分 · Word / PPT 输出规范

# 交付物输出规范

两种版式都从 `03-纪要初稿.md`（已通过质检）派生，**不要从 02-要点.md 直接生成**，否则会绕过证据与去重。

## 一、路由

| 交付物 | 路由到 | 说明 |
|---|---|---|
| `会议纪要.docx` | `tencent-docx` 技能 | Word 纪要版，正式、可编辑、可归档 |
| `会议汇报.pptx` | `tencent-pptx` 技能 | PPT 汇报版，用于会上回放或向上汇报 |
| `图文摘要.md` | 本技能直接写 | 要点卡片，便于贴到群/邮件 |
| `待确认清单.md` | 本技能直接写 | 格式见 `evidence-and-qc.md` 第八节 |

不提"Word 版/PPT 版"时，按 Phase 0 问到的输出形态执行；用户没说的默认两者都给。

## 二、Word 纪要版版式

- 纸张 A4，页边距 2.5cm；正文 10.5pt（五号），行距 1.5
- **标题用衬线字体**（宋体 / 思源宋体），**正文用黑体**（微软雅黑 / 思源黑体）
- 主色：蓝色莫兰迪（`#5B7C99` 系列）；分隔线、表格表头用主色
- 首页页眉信息条（一行）：会议名｜时间｜地点｜参会人
- 章节标题带主色左侧边条，与"金句块"风格统一
- **每条关键决策/行动项在条目下方用小一号灰字标注出处**：`[原文 00:12:30 · 张三]`
- 文末附录两张表：`附录A 决策清单`（决策 / 依据 / 状态 / 出处）、`附录B 行动项清单`（事项 / 责任人 / 交付物 / 截止日 / 状态）
- "未找到出处"的条目统一灰底，视觉上提示这是待确认内容

Word 纪要的读者要能**只看附录 A、B 就掌握全部决策与待办**，正文是给需要上下文的人看的。

## 三、PPT 汇报版页序（8-12 页，硬上限 12 页）

| 页 | 内容 | 备注 |
|---|---|---|
| 1 | 封面 | 会议名 / 时间 / 地点 / 参会人 / 纪要人 |
| 2 | 会议背景与目标 | ≤3 条，每条一行 |
| 3 | 核心结论速览 | ≤5 条，每条带状态色标 |
| 4-6 | 议题要点 | 一议题一页，最多 3 页；每页 ≤4 条 |
| 7 | 决策清单 | 表：决策 / 依据 / 状态 / 出处 |
| 8 | 行动项 | 表：事项 / 责任人 / 截止日 / 状态 |
| 9 | 待确认与风险 | 与 `待确认清单.md` 同源 |
| 10 | 附录：术语 / 数据来源 | 可省 |

页数不够 12 页不要硬凑；议题超过 3 个时，把次要议题合并进一页并注明"其余议题见 Word 纪要"。

## 四、配色与状态色标

沿用蓝色莫兰迪主色系：

| 用途 | 色值 | 说明 |
|---|---|---|
| 主色（标题条、表头） | `#5B7C99` | 蓝色莫兰迪 |
| 浅底 | `#EDF2F7` | 表格隔行、金句块背景 |
| 已确认 / 已决策 | `#5B7C99` 蓝 | 中性肯定 |
| 待确认 / 待定 | `#8A8F98` 灰 | 视觉上"未定" |
| 风险 / 已否决 | `#B4646B` 暗红 | 风险提示 |
| 已延期 | `#A08A63` 暗金 | 推迟 |

一张 PPT 里状态色不超过三种；色标必须与文字标签同时出现，不单靠颜色传达信息（投影仪色差会吃掉颜色）。

## 五、命名与落盘

- 落盘到会议工作目录 `<会议名>_纪要/`
- 文件名固定：`会议纪要.docx`、`会议汇报.pptx`、`待确认清单.md`、`图文摘要.md`
- 同一次会议重复生成 → 覆盖同名文件；**不要**建 `会议纪要_v2.docx`（版本靠 checkpoints.md 追溯）

## 六、常见坑

- **PPT 塞满正文** → 汇报版不是纪要的缩小版。一页一观点，细节指向 Word 纪要。
- **Word 里掉了出处** → 出处的意义就是让人能复核。Word 版必须保留出处，只是换成小字号。
- **两版数字不一致** → 两版务必从同一个 03 文件派生。发现不一致说明是手工改的，回退重出。
- **把"待确认"从 PPT 里删掉** → 待确认项是汇报的重点之一，不是要藏起来的东西。
- **忘了图文摘要** → 群里转发用的是图文摘要，不是 pptx。
